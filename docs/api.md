# api.md — API сервисов

> Контракты между фронтендом, сервисом-агрегатором и модельным сервисом.
> ML-логика живёт в `ml/` и здесь не описывается — см. [`ML.md`](../ML.md).

---

## 1. Схема

```
Frontend ──HTTP/JSON──▶ Aggregator (backend/aggregator-service/, Go, :8000) ──HTTP/JSON──▶ Model service (:8001)
                         · валидация входа                              · ml.pipeline.Pipeline.analyze()
                         · сессии диалога                               · предобработка и исправления,
                                                                          поиск, сужение; без состояния
                                   │
                                   ▼
                              Redis (:6379)
```

**Агрегатор** — единственная точка входа для фронтенда. Проверяет вход (длина, не пустой),
пересылает текст как есть и ответы пользователя в модельный сервис и хранит сессию уточняющего
диалога. Вся обработка текста — нормализация (`ml.text.normalize`), опечатки, раскладка — в
пайплайне, за один проход; токены и леммы модель строит сама.

**Модельный сервис** не хранит состояние: в каждый вызов передаётся весь текст и все ответы
пользователя, данные к этому моменту. Агрегатор хранит их в сессии, поэтому фронтенд присылает
только очередной ответ.

---

## 2. Архитектура агрегатора

Go 1.26, `net/http` из стандартной библиотеки, Redis через `github.com/redis/go-redis/v9`,
логи через `go.uber.org/zap`. Таблицы с товарами читают `github.com/xuri/excelize/v2` (`.xlsx`) и
`github.com/shakinm/xlsReader` (`.xls`); `.csv` — стандартная библиотека.

```
backend/aggregator-service/
  cmd/aggregator/          main: конфиг, логгер, сигналы SIGINT/SIGTERM → app.Run
  internal/
    app/                   Run: сборка слоёв, HTTP-сервер, graceful shutdown
    config/                настройки из переменных окружения
    logger/                zap-логгер; request_id и логгер запроса в context
    domain/                сущности (Session, Answer, AnalysisResult) и доменные ошибки с кодами
    service/               сценарий диалога: проверка → модель → сессия; то же для каждого товара таблицы
    sheet/                 чтение загруженной таблицы (.csv, .xlsx, .xls) в строки ячеек
    repository/            интерфейс SessionRepository и его реализация на Redis
    database/              подключение к Redis
    client/model/          клиент модельного сервиса (POST /analyze), проверка его ответа
    transport/http/        маршруты, схема ответа фронтенду, коды ошибок → HTTP-статусы, CORS,
                           request_id и строка лога на каждый запрос; openapi.yaml и страница /docs
```

Зависимости направлены только вниз: `transport/http → service → repository → domain`.
Сервис работает с сессиями только через интерфейс `repository.SessionRepository`, о Redis не
знает; модель — через интерфейс `service.Model`, его реализует `client/model`. Конкретные
реализации создаёт и связывает `app.Run`. HTTP-статусы знает только `transport/http`.

- **Graceful shutdown.** По SIGINT/SIGTERM сервер перестаёт принимать соединения, ждёт текущие
  запросы до `SHUTDOWN_TIMEOUT_S` (8 с), затем закрывает Redis и завершается с кодом 0. Время от
  SIGTERM до SIGKILL задано явно — `stop_grace_period: 10s` в compose (для `docker run` —
  `--stop-timeout 10`): умолчание Docker разное, `docker stop` на Docker 29.8 убивал контейнер через 3 с. Не уложившиеся в таймаут запросы обрываются, код
  выхода 1. Повторный сигнал завершает процесс сразу.
- **Логи** — `zap`, текстовые строки в stderr (`docker compose logs -f backend`), уровень —
  `LOG_LEVEL`. На каждый запрос одна строка `request`: метод, путь, статус, `duration_ms`; у ошибок —
  причина в поле `error`, 5xx пишутся с уровнем `ERROR`. `request_id` берётся из заголовка `X-Request-ID`
  (символы `A-Za-z0-9._:-`, до 128 — то же правило, что у модели) или генерируется; он
  возвращается в заголовке `X-Request-ID` ответа и в теле ошибок, передаётся в модельный сервис и
  пишется во все строки логов запроса — по нему запрос находится в логах обоих сервисов.
- **Сессии хранятся в Redis** (`repository.RedisSessionRepository`): одна JSON-строка под ключом
  `session:<id>`. TTL — `SESSION_TTL_S`, продлевается при каждом чтении и записи; неактивные
  сессии удаляются сами. Агрегатор при старте проверяет Redis (`PING`) и не запускается без него.
  Каждая операция с Redis ограничена 3 секундами: если Redis упал, запрос получает
  `503 storage_unavailable`, а не висит.

## 3. API агрегатора (для фронтенда)

Базовый URL: `http://localhost:8000`.

**Swagger.** Тот же контракт в формате OpenAPI 3 —
[`openapi.yaml`](../backend/aggregator-service/internal/transport/http/openapi.yaml). Запущенный
агрегатор показывает его в Swagger UI на `http://localhost:8000/docs` (запросы можно выполнять
прямо со страницы) и отдаёт сам файл на `http://localhost:8000/docs/openapi.yaml`. Скрипты
Swagger UI загружаются с CDN, поэтому странице нужен интернет. Через nginx фронтенда (`:8080`)
страница недоступна: он проксирует только `/api/`. Файл пишется вручную — при изменении маршрутов
или полей ответа он обновляется вместе с этим документом.

### Сценарий

```
POST /api/v1/analyze {text}
   │
   ▼
next_step != null ──▶ показать вопрос и options ──▶ POST /api/v1/sessions/{id}/answers {value}
   │                                                                  │
   │◀─────────────────────────────────────────────────────────────────┘
   ▼
next_step == null, ktru != null  → итоговый код
next_step == null, ktru == null  → товар не найден в КТРУ (см. errors), вопросов нет
```

### `POST /api/v1/analyze`

Создаёт сессию по описанию товара.

Запрос:

```json
{"text": "стл офисный на колесиках, кожзам, высота 110 см"}
```

| Поле | Тип | Ограничения |
|---|---|---|
| `text` | string | не пустой и не только из пробелов и невидимых символов; не длиннее `MAX_TEXT_LENGTH` символов (по умолчанию 2000). В модель уходит как есть |

Ответ `200` (одинаковый для обоих эндпоинтов):

```json
{
  "session_id": "2SCEM3LPMN6KXPWDQELGXAZFAV",
  "corrections": [
    {"from": "стл", "to": "стул", "reason": "опечатка (отличается на 1 симв.)"},
    {"from": "кожзам", "to": "искусственная кожа", "reason": "приведено к значению КТРУ («Материал обивки»)"}
  ],
  "characteristics": [
    {"name": "Колесные опоры", "value": "Да", "source": "на колесиках", "origin": "ktru", "confidence": 0.9},
    {"name": "Материал обивки", "value": "Искусственная кожа", "source": "кожзам", "origin": "ktru", "confidence": 0.85},
    {"name": "Высота", "value": "1000–1200", "unit": "Миллиметр", "source": "110 см", "origin": "ktru", "confidence": 0.95}
  ],
  "candidates": [
    {"code": "31.01.11.150-00000003", "name": "Стул офисный", "score": 0.93},
    {"code": "31.01.11.150-00000007", "name": "Кресло офисное", "score": 0.88}
  ],
  "candidates_total": 2,
  "errors": [],
  "missing_required": ["Наличие подлокотников"],
  "next_step": {
    "message": "Подходит 2 кода КТРУ. Укажите характеристику:",
    "characteristic": "Наличие подлокотников",
    "options": ["Да", "Нет"]
  },
  "ktru": null,
  "ktru_name": null,
  "steps": [
    {"stage": "Поиск по описанию", "count": 23},
    {"stage": "Высота = 1000–1200 Миллиметр", "count": 2}
  ]
}
```

| Поле | Описание |
|---|---|
| `session_id` | идентификатор сессии для ответа на вопрос (непрозрачная строка) |
| `corrections[]` | `from` → `to`, `reason`: опечатки, раскладка, приведение слов к значениям КТРУ |
| `characteristics[]` | `name`, `value`, `unit` (**только у числовых**, иначе поля нет), `source` — фрагмент текста пользователя, из которого извлечено значение; `origin` — источник: `ktru` (справочник КТРУ), `portal` (справочник Портала поставщиков), `new` (новая характеристика), `answer` (выбрана пользователем из вариантов КТРУ); `confidence` — уверенность извлечения, 0–1 |
| `candidates[]` | оставшиеся коды КТРУ: `code`, `name`, `score` (не больше 20) |
| `candidates_total` | сколько кодов КТРУ подходит всего; `candidates[]` — первые из них |
| `errors[]` | `type`, `severity`, `message`; если есть — `characteristic`, `suggestion`. `severity`: `error` — ошибка в описании, `warning` — стоит проверить, `info` — уведомление, не ошибка (например, `not_in_ktru`: характеристики вне КТРУ сохранены и на выбор кода не влияют). Типы — в [`ML.md`](../ML.md) |
| `missing_required[]` | обязательные характеристики КТРУ оставшихся позиций, которых нет в описании; пусто, когда код определён или товар не найден |
| `next_step` | вопрос пользователю или `null`. `characteristic` — название характеристики; `null`, когда спрашиваем, какой товар или какой код выбрать (тогда `options` — названия товаров или коды) |
| `ktru`, `ktru_name` | итоговый код и наименование, когда код определён однозначно; иначе `null` |
| `steps[]` | как сужался список кодов: `stage` — шаг, `count` — сколько кодов осталось после него |

### Контекст и счётчики

Ответ также содержит `product_intent` (лемма товара), `subtype_context[]` (контекстные слова),
`retrieval_count` (кандидаты после семантического поиска и порога), `compatible_count`
(после проверки названия товара) и `remaining_count` (после КТРУ-ограничений).
`next_question` дублирует `next_step` в ответе модели и агрегатора; интерфейс
по-прежнему использует `next_step`.

У `characteristics[]` поле `source` теперь означает происхождение: `ktru`, `portal` или `user`.
Исходный фрагмент текста находится в `user_text`. Поля `used_for_narrowing` и
`used_for_reranking` показывают, где признак реально применён. Те же флаги и `source`
есть у `subtype_context[]`. Контекст и признаки Портала меняют порядок кандидатов,
но не исключают код КТРУ. `candidates[]` возвращаются в порядке после ранжирования.

Словарь Портала строится командой `python -m ml.portal build` из трёх XLSX в
`data/raw/supplier_portal/`; результат `data/processed/portal_characteristics.json`
содержит названия, значения, алиасы характеристик и частоты слов в названиях товаров.
Он игнорируется Git и монтируется в модельный сервис через Docker Compose.
При отсутствии артефакта сервис запускается, но признаки второго уровня Портала недоступны.

Агрегатор сокращает полный ответ модели (`ML.md`) до этих полей.

### `POST /api/v1/analyze/batch`

Создаёт сессии сразу для всех товаров из таблицы. Каждый товар обрабатывается так же, как текст в
`POST /api/v1/analyze`, и получает свою обычную сессию: на её вопросы отвечают через
`POST /api/v1/sessions/{session_id}/answers`.

Запрос — `multipart/form-data` с файлом в поле `file`:

```bash
curl -s -X POST localhost:8000/api/v1/analyze/batch -F 'file=@products.xlsx'
```

| Что | Правило |
|---|---|
| Формат | `.csv`, `.xlsx` или `.xls`, определяется по расширению имени файла. Из книги Excel читается первый лист |
| Размер | тело запроса не больше `MAX_BODY_BYTES` (по умолчанию 1 МБ) |
| CSV | кодировка UTF-8 (с BOM или без) или Windows-1251; разделитель определяется по первой строке: табуляция, иначе `;`, иначе `,`. При разделителе `,` описание с запятыми берётся в кавычки |
| Колонки | если в первой непустой строке есть заголовок, начинающийся с «Описание», «Характеристики» или `Description`, колонки берутся по заголовкам; название — колонка с заголовком на «Название», «Наименование», «Товар» или `Name`. Без такой строки заголовков нет: первая занятая колонка — название, следующая — описание; если занята одна колонка, это описание |
| Товар | строка с непустым описанием. Название необязательно; строка с одним названием и пустые строки пропускаются |
| Сколько товаров | не больше `MAX_BATCH_ITEMS` (по умолчанию 50) |

В модель уходит «название, описание»; если названия нет или описание уже содержит его — только
описание. Товары обрабатываются параллельно, по `BATCH_CONCURRENCY` (по умолчанию 4).

Ответ `200`:

```json
{
  "items": [
    {
      "row": 2,
      "name": "Стул",
      "description": "офисный на колесиках, кожзам, высота 110 см",
      "result": {"session_id": "2SCEM3LPMN6KXPWDQELGXAZFAV", "...": "как в ответе POST /api/v1/analyze"}
    },
    {
      "row": 5,
      "description": "…",
      "error": {"code": "invalid_text", "message": "Описание длиннее 2000 символов"}
    }
  ]
}
```

| Поле | Описание |
|---|---|
| `items[]` | товары в порядке строк таблицы |
| `row` | номер строки в файле, с 1 |
| `name` | название товара; поля нет, если названия нет |
| `description` | описание товара из файла |
| `result` | результат анализа в формате `POST /api/v1/analyze`, с `session_id` |
| `error` | `code` и `message`, если товар не обработан: коды те же, что в таблице ошибок ниже (`invalid_text`, `model_*`, `storage_unavailable`). В элементе есть либо `result`, либо `error` |

Ошибка одного товара не отменяет остальные: запрос отвечает `200`, если файл прочитан и товары в
нём найдены. Ошибки самого файла — в таблице ошибок ниже.

### `POST /api/v1/sessions/{session_id}/answers`

Ответ на текущий вопрос `next_step`. Фронтенд присылает только выбранный вариант; тип вопроса
и характеристику агрегатор берёт из сохранённого `next_step`, добавляет ответ к сессии, заново
вызывает модель с текстом сессии и всеми ответами и возвращает обновлённый результат (формат как выше).

```json
{"value": "Нет"}
```

| Поле | Правило |
|---|---|
| `value` | один из `next_step.options`, строка в точности |

### `GET /health`

`200 {"status": "ok"}` — процесс агрегатора жив. Доступность модели не проверяет.

### Ошибки

Единый формат для всех ошибок:

```json
{"error": {"code": "invalid_answer", "message": "Выберите один из предложенных вариантов",
           "request_id": "PJ7XQ2M4ZK3LDW5RBNC6YTHF2A"}}
```

`message` — короткий текст для пользователя на русском, без внутренних подробностей. Причина ошибки
(например, адрес недоступного сервиса) пишется только в лог агрегатора, в строку запроса с тем же
`request_id`. `request_id` совпадает с заголовком `X-Request-ID` ответа: по нему ищутся строки логов
агрегатора и модели.

| HTTP | `code` | Когда |
|---|---|---|
| 404 | `session_not_found` | сессии нет (неверный id или истёк TTL) — начать заново через `/analyze` |
| 404 | `not_found` | несуществующий маршрут |
| 409 | `no_pending_question` | в сессии нет вопроса (`next_step` = `null`) |
| 413 | `file_too_large` | загруженный файл больше `MAX_BODY_BYTES` |
| 422 | `validation_error` | тело запроса не соответствует схеме; подробности в `error.details` |
| 422 | `invalid_text` | текст пустой или слишком длинный |
| 422 | `invalid_answer` | `value` не входит в `next_step.options` |
| 422 | `invalid_file` | файл не `.csv`/`.xlsx`/`.xls`, не читается, в нём нет товаров или их больше `MAX_BATCH_ITEMS` |
| 502 | `model_bad_response` | модель вернула не-200 или ответ не в ожидаемом формате |
| 503 | `model_unavailable` | модельный сервис недоступен |
| 503 | `storage_unavailable` | Redis недоступен |
| 504 | `model_timeout` | модель не ответила за `MODEL_TIMEOUT_S` |

## 4. Контракт модельного сервиса (агрегатор → модель)

Агрегатор вызывает один эндпоинт. Это тонкая HTTP-обёртка над `Pipeline.analyze()` из
`ml/pipeline.py`: тело запроса передаётся в `analyze()` как есть, результат возвращается как есть.

> **Статус:** HTTP-обёртки модельного сервиса в репозитории пока нет — `Pipeline` вызывается
> только из Python. Агрегатор проверен против фейкового сервера с ответами в формате `ML.md`.

### `POST /analyze`

Запрос:

```json
{
  "raw": "стл на металлическом каркасе",
  "answers": [
    {"type": "characteristic", "characteristic": "Наличие подлокотников", "value": "Нет"}
  ]
}
```

| Поле | Описание |
|---|---|
| `raw` | текст пользователя как есть |
| `answers` | все ответы пользователя по порядку; `[]` при первом запросе |

Ответ `200` — результат `Pipeline.analyze()` (см. [`ML.md`](../ML.md#формат-ответа)). Агрегатор
требует обязательные поля `input`, `text`; для `next_step` — `type`, `message`, `options`.
Любой другой статус или формат агрегатор превращает в `502 model_bad_response`.

## 5. Настройки агрегатора

В Docker значения берутся из [`deployment/aggregator.env`](../deployment/aggregator.env); при локальном
`go run` незаданные переменные получают значения по умолчанию из `backend/aggregator-service/internal/config/config.go`.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `LOG_LEVEL` | `info` | уровень логов: `debug`, `info`, `warn`, `error` (регистр не важен) |
| `LISTEN_ADDR` | `:8000` | адрес HTTP-сервера |
| `SHUTDOWN_TIMEOUT_S` | `8` | сколько секунд ждать завершения запросов при остановке |
| `READ_HEADER_TIMEOUT_S` | `10` | таймаут чтения заголовков запроса, секунды |
| `MAX_BODY_BYTES` | `1048576` | максимальный размер тела запроса, байты; он же ограничивает загружаемый файл |
| `MODEL_SERVICE_URL` | `http://localhost:8001` (в Docker — `http://model:8001`) | адрес модельного сервиса |
| `MODEL_TIMEOUT_S` | `30` | таймаут запроса к модели, секунды |
| `MAX_TEXT_LENGTH` | `2000` | максимальная длина текста |
| `MAX_BATCH_ITEMS` | `50` | сколько товаров принимается в одной таблице |
| `BATCH_CONCURRENCY` | `4` | сколько товаров таблицы обрабатывается одновременно |
| `REDIS_URL` | `redis://localhost:6379/0` (в Docker — `redis://redis:6379/0`) | адрес Redis для сессий |
| `REDIS_PING_TIMEOUT_S` | `5` | таймаут проверки Redis при старте, секунды |
| `REDIS_OP_TIMEOUT_S` | `3` | таймаут одной операции с Redis, секунды |
| `SESSION_TTL_S` | `3600` | сколько секунд хранится неактивная сессия |
| `CORS_ORIGINS` | `*` | разрешённые origin фронтенда через запятую |
