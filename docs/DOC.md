## 1. Одним абзацем

Мы строим **сервис стандартизации товарных характеристик** для поставщиков и покупателей Портала поставщиков. Поставщик описывает размещаемый товар, а покупатель — потребность для закупки. Сервис определяет категорию товара, извлекает характеристики, приводит их названия, значения и единицы к стандарту справочника КТРУ, постепенно сужает множество подходящих позиций до одного конечного кода, а если данных не хватает — сам задаёт пользователю наиболее полезный уточняющий вопрос. Попутно находит ошибки в описании и объясняет, почему считает их ошибками.

**Это не «нейросеть, угадывающая код».** Это система, где ML отвечает за понимание свободного текста, а финальное решение принимается проверяемыми правилами по справочнику — поэтому результат объясним и воспроизводим.

## 2. Глоссарий

| Термин | Что это |
|---|---|
| **Портал поставщиков** | zakupki.mos.ru — маркетплейс для госзакупок малого объёма |
| **СТЕ** | Стандартная товарная единица. Одна карточка товара, к которой разные поставщики добавляют свои ценовые предложения. В каталоге > 3 млн позиций |
| **КТРУ** | Каталог товаров, работ и услуг. Нормативный справочник стандартизированных позиций. **Наш главный эталон** |
| **Позиция КТРУ** | Запись справочника: код, наименование, описание, характеристики, допустимые значения, единицы |
| **Конечный код КТРУ** | `25.73.30.141-00000001`. **Обозначает группу товаров, а не конкретную модель** |
| **ОКПД2** | Классификатор продукции. Первая часть кода КТРУ (`25.73.30.141`) |
| **Характеристика** | Свойство товара: «Длина рукоятки», «Материал обивки» |
| **Корзина (bucket)** | Допустимое значение числовой характеристики в КТРУ — это **диапазон**, а не число: `200 - 300 Миллиметр` |
| **Товар** | Главное слово наименования в описании пользователя: «молоток», «стул» (`product_intent`). Вместе с категорией — ключ профиля товара и новых характеристик |
| **Профиль товара** | Какие характеристики и с какими значениями реально заполняют в карточках СТЕ этого товара на Портале. Строится по выгрузкам |

### Ключевое про отличие от обычного маркетплейса

На обычном маркетплейсе 100 продавцов создают 100 карточек одного товара. На Портале поставщиков существует **одна стандартизированная позиция**, к которой все прикрепляют предложения. Система помогает поставщику правильно описать и классифицировать размещаемый товар, а покупателю — сформировать стандартизированное описание потребности и выбрать подходящую позицию КТРУ.

### Конечный код — это группа

Офисные стулья разного цвета и размера могут относиться к одному коду КТРУ, если позиция допускает эти значения характеристик. Мы **не ищем конкретную модель** — мы находим группу, в которую товар попадает по своим характеристикам.

| Источник | Объём | Где в проекте | Роль |
|---|---|---|---|
| `nsiKTRUNew_all-actual_*.xml` | 1839 позиций трёх категорий, в работе 1209 | `data/processed/ktru.parquet` (в git) | **Главный эталон** |

**Категории: одежда, мебель, инструменты.** Остальное обрабатывать не требуется. Категория позиции КТРУ определяется по префиксу ОКПД2 в `ml/config/ktru_categories.json`: одежда — `14`, мебель — `31`, инструменты — `25.73` и `28.24`. Новая категория добавляется строкой в этом файле.

### Справочник КТРУ

Подготовка — `scripts/prepare_ktru_dataset.py` (парсер в `ml/data/`): из XML берутся позиции трёх категорий, по каждому коду — **одна, последняя версия**. Результат — `data/processed/ktru.parquet`: 1839 позиций, повторов кода нет.

Сервис (`ml/ktru.py`) загружает из них только:

| Фильтр | Осталось позиций |
|---|---:|
| действующие (`ACTIVE`; 353 `TERMINATED` отброшены) | 1486 |
| конечные, не шаблоны | 1238 |
| товары, не услуги («Услуги по производству…») | **1209**: одежда 769, мебель 254, инструменты 186 |

Характеристики, помеченные в архиве `actual: false`, не загружаются. У позиции в среднем 4.8 характеристики, максимум 27.

### Что извлекаем из КТРУ

код · наименование · **текстовое описание** · ОКПД2 · актуальность · **версия позиции (берём актуальную)** · характеристики · допустимые значения и диапазоны · единицы · обязательность характеристики · связи с родительскими позициями.

> Описания позиций сохраняем и используем в поиске — организаторы отдельно это подчеркнули. Но в актуальном архиве описание есть только у 12 из 1209 позиций, поэтому основной сигнал поиска — наименование и названия характеристик.

### Выгрузки Портала

Из трёх файлов собираются два артефакта. Оба построены на данных организаторов, поэтому не входят ни в git, ни в Docker-образ: лежат в `data/processed/` и подключаются в контейнер модели томом только для чтения. **При запуске они не создаются** — их собирают заранее:

| Команда | Результат | Что внутри |
|---|---|---|
| `python -m ml.portal build` (~6 мин) | `portal_characteristics.json` (~11 МБ) | справочник характеристик по категориям (вкладка 2) и профили товаров по карточкам СТЕ (вкладка 1). Только актуальные характеристики: «Базовая» и «Эталонная», заполненные в карточках |
| `python -m ml.newchar build` (~40 с) | `newchar_model.pkl` (~300 КБ) | классификатор «подходит ли характеристика товару» (раздел 5) |

Без словаря сервис работает, но уровень «Портал» пропускается: всё, чего нет в КТРУ, становится новыми характеристиками, а в лог об этом ничего не пишется. Без классификатора новые характеристики проверяют только правила, в лог пишется предупреждение. **Перед демо наличие обоих файлов на сервере проверяется вручную.**

### Порядок изучения данных

Рекомендация организаторов: **сначала реальные выгрузки Портала, потом КТРУ.** Выгрузки показывают, как люди реально называют товары и свойства; КТРУ показывает, к чему это надо привести. Товар из выгрузки можно найти на портале по идентификатору и посмотреть, как характеристики выглядят в интерфейсе.

### Выгрузки — не просто справочник

600 000+ реальных карточек дают нам три вещи, которые негде больше взять:

1. **Словарь алиасов**: как люди на самом деле пишут («вес» → «Масса», «кожзам» → «Искусственная кожа»).
2. **Второй приоритет характеристик**: то, чего нет в КТРУ, но что реально используется.
3. **Автоматический бенчмарк**: `eval/portal.py` строит запросы из реальных карточек — название СТЕ и название с двумя характеристиками, 1200 примеров. Кода КТРУ в выгрузках нет, эталон — категория файла.

## 5. Иерархия источников характеристик

Это обязательная бизнес-логика, прямо озвученная организаторами и повторённая жюри.

```
1. КТРУ               есть характеристика? → используем её название и формат
   ↓ нет
2. Выгрузки Портала   заполняется в карточках СТЕ этого товара или есть в справочнике категории? → берём оттуда
   ↓ нет
3. Встречалась раньше была в другом описании этого же товара? → source = "new", known = true
   ↓ нет
4. Новая              подходит этому товару? → создаём, source = "new"
```

В интерфейсе и в API источник — поле `origin`: `ktru`, `portal`, `new` или `answer` (значение выбрано пользователем из вариантов КТРУ). В сужении кодов участвуют только `ktru` и `answer`.

На шаге 1 у позиции КТРУ есть обязательные характеристики. Если пользователь их не указал, сервис подсказывает:
«Вы не ввели обязательные характеристики товара: …» (предупреждение `missing_required`); код при этом определяется
как обычно. Характеристики КТРУ с `actual: false` в архиве не используются.

На шаге 2 «товар» — это категория и главное слово названия («инструменты / молоток»). Из выгрузок берутся только
актуальные характеристики: в справочнике Портала они «Базовая» или «Эталонная», не служебные («Вид продукции») и
реально заполнены в карточках. Признак, найденный на Портале, на выбор кода КТРУ не влияет — он может только
поменять порядок кандидатов. Словарь Портала общий на категорию, поэтому характеристика Портала, которой нет ни в
одной из 50+ карточек этого товара, дополнительно проверяется так же, как новая (ниже).

Каждая новая характеристика, которая подходит товару, сохраняется в Postgres модельного сервиса с ключом
(категория, товар, леммы названия) — так шаг 3 узнаёт её в следующих описаниях. Повтор того же
описания (следующий раунд диалога) не считается: известной характеристику делает только
другое описание. Postgres недоступен — шаг 3 пропускается, остальное работает.

### Что подходит товару, а что нет

Новой характеристикой становится не любая фраза из описания. Проверка выполняется в сервисном слое модели
(`ml/service/analysis.py`) для характеристик `new` и `portal`:

1. **Правила** (`ml/fit.py`):
   - только оценочные слова — «классная», «модная», «отличного качества»;
   - размерность, которой у товаров категории не бывает — «стол, объём двигателя 2 л», «футболка, мощность 800 Вт».
     У товара с 30+ карточками на Портале размерность проверяется по его собственному профилю: литры бывают у
     бензопил, но не у молотка;
   - слово чужой категории — «брюки, цвет лдсп серый». Если своя категория использует слово очень редко — не отказ,
     а просьба подтвердить.
2. **Классификатор** (`ml/newchar.py`): логистическая регрессия на эмбеддингах уже загруженной модели поиска
   (вторая нейросеть не нужна). Ответ — «подходит», «не уверен» или «не подходит».

| Итог | В карточке товара | Сообщение пользователю | Запоминается |
|---|---|---|---|
| подходит | да | — | да |
| не уверен | да | `uncertain_characteristic`: «подтвердите, что признак относится к товару» | нет |
| не подходит | **нет** | `not_fitting_characteristic` с причиной | нет |

### Что не считается характеристикой

Разбор описания (`ml/pipeline.py`) отделяет то, что характеристикой не является:

- **бренд, модель, артикул** («Bosch», «CH-868», названия в кавычках) — уведомление `brand_or_model`; в подборе не участвуют, но и не теряются;
- **нечитаемый фрагмент** («ыврпаоы») — предупреждение `unreadable_fragment` «Поясните, что имелось в виду»; в интерфейсе у него кнопка «Пояснить фрагмент»;
- **название характеристики без значения** («шкаф, материал изготовления») — предупреждение `missing_value` с просьбой указать значение.

**Запрещено удалять характеристику только потому, что её нет в КТРУ.** Пользователь написал «противоскользящая рукоятка» — этого нет в справочнике, но информация ценная и должна попасть в карточку СТЕ. Не попадает в карточку только то, что товару не подходит (см. выше), и пользователь видит причину.

**Обязательно показывать происхождение** каждой характеристики в интерфейсе. Это отдельное требование, и оно почти ничего не стоит в реализации: у каждой строки таблицы — бейдж «КТРУ», «Портал поставщиков», «Новая характеристика» или «Ответ пользователя» и исходный фрагмент описания.

### Этапы пайплайна (`ml/pipeline.py`)

| # | Этап | Модуль | Что делает |
|---|---|---|---|
| 1 | Нормализация и исправления | `ml/text.py`, `ml/correct.py` | ё, кавычки, сокращения; неверная раскладка; опечатки, пропуски и перестановки букв — по словарю КТРУ |
| 2 | Поиск кандидатов | `ml/search.py` | эмбеддинги `intfloat/multilingual-e5-small` по документу «наименование + описание + названия характеристик»; ищем по всему тексту и по первому фрагменту (название товара); оставляем коды не дальше 0.03 от лидера; ниже порога — «товар не найден» |
| 3 | Характеристики КТРУ | `ml/sizes.py`, `ml/units.py`, `ml/numwords.py`, `ml/values.py` | размеры одежды; числа и единицы с переводом в единицу КТРУ и попаданием в диапазон; габариты «120х60х75 см»; текстовые значения, синонимы, отрицания |
| 4 | Сужение | `ml/narrow.py` | по наименованию, затем по характеристикам: кандидат отбрасывается только при прямом противоречии справочнику, без характеристики остаётся ниже; подозрительные значения код не выбирают |
| 5 | Портал и новые | `ml/portal.py`, `ml/pipeline.py` | бренды, нечитаемое, названия без значений; словарь Портала; новые характеристики; переранжирование по контексту |
| 6 | Вопрос и итог | `ml/narrow.py`, `ml/pipeline.py` | разные наименования — «какой товар»; одно наименование — характеристика, ответ на которую в среднем оставляет меньше всего кодов; позиции не различаются — выбор кода. Ошибки с уровнями, недостающие обязательные характеристики, итоговый код |

После пайплайна сервисный слой (`ml/service/analysis.py`) проверяет, подходят ли товару характеристики Портала и новые (раздел 5), и отмечает уже встречавшиеся по Postgres.

### Ключевые решения

- **Состояние диалога хранит агрегатор** (Redis), модель его не хранит: в каждый вызов приходят весь текст и все ответы пользователя. Фронтенд присылает только очередной ответ.
- **Модель обрабатывает один запрос за раз**: пайплайн не потокобезопасен. Масштабирование — числом процессов и контейнеров модели.
- **Сервис деградирует, а не падает:** без Postgres пропускается шаг «встречалась раньше», без словаря Портала — уровень Портала, без классификатора остаются правила. Без Redis агрегатор не запускается.
- **Скорость:** модель отвечает за p50 ≈ 12 мс и p95 ≈ 14 мс в Docker на 4 потоках CPU, проверка новых характеристик добавляет около 16 мс. Видеокарта не нужна. Замеры и условия — в [`ML.md`](../ML.md).
- **Сквозной `request_id`:** агрегатор берёт его из заголовка `X-Request-ID` или создаёт, передаёт в модель, и оба сервиса пишут его в каждую строку лога.

### Запуск и развёртывание

```bash
docker compose -f deployment/docker-compose.yaml up --build
# интерфейс http://localhost:8080 · API http://localhost:8000 (Swagger /docs) · модель http://localhost:8001
```

Пять контейнеров: `frontend`, `backend`, `model`, `redis`, `postgres`. Push в `main` разворачивает стек на сервере (`.github/workflows/deploy.yml`).

## 7. Семь инвариантов проекта

Это то, что проверяется на код-ревью и спрашивается на защите. Нарушение любого — потеря баллов.

| # | Инвариант | Почему | Где обеспечено |
|---|---|---|---|
| 1 | КТРУ — главный эталон, но **не единственный источник** | Характеристики вне КТРУ сохраняем через Портал или как новые | `origin`: `ktru` → `portal` → `new` |
| 2 | **Ничего не теряем.** Характеристика без места в КТРУ не удаляется. В карточку не попадает только то, что товару не подходит, — с объяснением причины | Прямое требование организаторов; жюри: «новым свойством не должна становиться любая фраза» | `ml/pipeline.py`, `ml/service/analysis.py` |
| 3 | **Показываем происхождение** каждой характеристики | Отдельное требование к UI | бейджи источника в `frontend/src/results.tsx` |
| 4 | **Характеристики принадлежат категории.** `(category, name)` | Одинаковые названия в разных категориях — разные сущности | словарь Портала по категориям, ключ новых характеристик в Postgres |
| 5 | **Нельзя произвольно выбирать код**, если подходит несколько | Обязаны задать уточняющий вопрос | `ml/narrow.py`: вопросы `product`, `characteristic`, `code` |
| 6 | **Ошибку мало исправить — надо объяснить**, почему она ошибка | Прямое требование | `message` и `suggestion` у каждой ошибки, «Как исправить» в UI |
| 7 | Конечный код — **группа товаров**, не модель | Влияет на формулировки в UI и на защите | итог в UI — «Позиция КТРУ» |

## 8. Что оценивается

| Критерий | Баллы | Где в проекте |
|---|---:|---|
| Функциональность и качество решения | **40** | весь путь от текста до кода КТРУ: пайплайн (раздел 6), агрегатор, интерфейс |
| Техническая реализация и масштабируемость | 16 | архитектура (раздел 6), индексы в памяти, скорость, категории задаются конфигом |
| Презентация, команда, защита | 15 | слайды, BPMN, репетиции |
| Распознавание ошибок | 12 | опечатки и раскладка — `ml/correct.py`; несуществующие значения, диапазоны, единицы, противоречия — `ml/values.py`, `ml/units.py`, `ml/narrow.py`; неподходящие характеристики — `ml/fit.py`, `ml/newchar.py` |
| Пользовательский интерфейс | 10 | `frontend/`: исправления, таблица с источниками и редактированием, история сужения, уточняющий вопрос, сообщения с подсказками «Как исправить» |
| Понимание предметной области | 7 | нарратив защиты, глоссарий, этот документ |

### Что жюри сказало прямым текстом

1. **Полностью работающая система.** Нельзя показывать несвязанные модули — фронт, бэк и обработка должны работать вместе. Это важнее качества каждого компонента по отдельности.
2. **Делать ровно ТЗ.** За функции вне задания баллов могут не начислить. Любая «а давайте ещё» — это минус время у обязательного.
3. **Интерфейс должен объяснять:** какие характеристики найдены, что исправлено, откуда каждая характеристика, почему ошибка, как сужается КТРУ.
4. **Сначала baseline на чистых данных, потом ошибки.** Не пытаться сразу построить умную систему, пока базовый путь не работает.
5. **Масштабируемость** — показать, что расширяется на другие категории.

### Замечания со встречи с жюри и как они учтены

| Замечание | Как учтено |
|---|---|
| Нельзя ограничиться КТРУ: КТРУ → выгрузки Портала → новая характеристика; новую запоминать для категории | раздел 5, Postgres |
| Выгрузки Портала — часть основного решения, а не дополнение | уровень `portal` и профили товаров; на демо обязательно наличие словаря (раздел 4) |
| Не всякая фраза — характеристика: чужое свойство («объём двигателя» у стола), субъективная оценка («классная майка») | `not_fitting_characteristic`: в карточку не добавляется, причина показывается |
| Непонятный фрагмент — попросить пояснение, сохранив сам фрагмент | `unreadable_fragment` и кнопка «Пояснить фрагмент» |
| Код однозначен — показать сразу, объяснив исправления и недостающие обязательные характеристики | итоговый код вместе с `corrections` и `missing_required` |
| Отсутствие обязательного свойства не блокирует определение кода | `missing_required` — предупреждение, а не отказ |
| Без лишних подтверждений вроде «Вы согласны с категорией?» | вопрос задаётся, только когда осталось больше одного кода |
| Старая и новая версии одной записи не должны быть разными кандидатами | при подготовке остаётся одна версия на код, `TERMINATED` отброшены, повторов кода нет |

### Как проверяем качество

Подробно — в [`ML.md`](../ML.md), раздел «Проверка».

- **325 запросов, построенных из КТРУ**, и те же запросы с искусственными опечатками (`eval/make_ktru_cases.py`, `eval/run.py`): правильное наименование первым — 0.939, F1 характеристик — 0.982. Оценка оптимистичная: запросы построены из того же справочника, по которому ищем.
- **1200 реальных карточек Портала** (`eval/portal.py`): товар найден — 0.79, категория верна — 0.97, ошибок — 5.2 на 100 описаний. Кода КТРУ в выгрузках нет, поэтому точность итогового кода на реальных данных не измерена.
- **Модель поиска** выбрана сравнением e5-small с FRIDA, BGE-M3 и reranker по качеству и задержке.

## 9. Ограничения

| Требование | Что это значит |
|---|---|
| ОС Linux + обязательный веб-интерфейс | docker-compose, всё воспроизводимо |
| Только **открытые** ML-модели | Никаких закрытых весов |
| ≤ 40 ГБ VRAM для инференса суммарно | Лимит высокий, но тяжёлые модели надо **обосновывать**. Используем `multilingual-e5-small` (~470 МБ, CPU) и логистическую регрессию поверх её эмбеддингов |
| Внешние API проприетарных LLM — запрещены | Решение не должно зависеть от OpenAI / Gemini / Claude |
| Платные поисковые API — запрещены | Поиск только свой |
| Low-code / no-code — запрещены | — |
| **AI для написания кода — разрешён** | Codex, ChatGPT и т.п. использовать можно |
