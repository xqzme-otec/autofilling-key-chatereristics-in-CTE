# ML-пайплайн: описание товара → характеристики КТРУ → код КТРУ

На вход — текстовое описание товара на естественном языке (с опечатками, неполное).
На выход — готовый JSON: исправления, унифицированные характеристики со значениями и единицами,
кандидаты КТРУ, ошибки с обоснованием, следующий уточняющий вопрос и итоговый код.

## Что сделано

| Этап | Файл | Что делает |
|---|---|---|
| Предобработка | `ml/text.py` | нормализация (ё, кавычки, «х/б»), токены, леммы (pymorphy3) |
| Исправление слов | `ml/correct.py` | опечатки, пропуски и перестановки букв, неверная раскладка → слова КТРУ (SymSpell по словарю КТРУ); при нескольких вариантах выбирает по контексту, остальные отдаёт в `alternatives` |
| Поиск кандидатов | `ml/search.py` | семантический поиск по позициям КТРУ (эмбеддинги `intfloat/multilingual-e5-small`) по документу `name + nsi_description + characteristic names`; `name_boost` настраивается в `ml/config/retrieval.json` |
| Текстовые значения | `ml/values.py` | слова пользователя → значения КТРУ: синонимы («кожзам» → «Искусственная кожа»), обобщения («хб» → «Натуральная»), отрицания («без капюшона» → «Отсутствует»), Да/Нет-характеристики («на колесиках» → «Наличие колесных опор: Да») |
| Числа и единицы | `ml/units.py`, `ml/numwords.py` | «110 см», «0,5кг», «52-54», «от 100 до 200 мм», «полтора килограмма» → перевод в единицу КТРУ и попадание в диапазон; число без характеристики КТРУ у товара уходит в Портал / новые |
| Портал и новые | `ml/portal.py` | признаки из описания, которых нет среди характеристик КТРУ товара (в любом месте текста). Сначала профиль товара — что реально заполняют в карточках СТЕ этого товара (вкладка 1 выгрузок): «стеклопластик» у молотка → «Материал рукоятки: Стеклопластик», «с обрезиненной ручкой» → «Обрезиненная ручка: Да»; затем справочник характеристик категории (вкладка 2) — «цвет синий» → «Цвет: синий», «в кейсе» → «Упаковка: Кейс»; иначе новая характеристика — «с противоскользящей рукояткой» → «Противоскользящая рукоятка: Да», «гарантия 3 года» → «Гарантия: 3 года». Ничего не выбрасываем; пользователь получает уведомление `not_in_ktru` |
| Сужение | `ml/narrow.py` | наименование → характеристики → уточняющий вопрос (какой товар / какая характеристика / какой код); история шагов; список недостающих обязательных характеристик. Кандидат отбрасывается только при прямом противоречии справочнику; без характеристики — остаётся, но ниже (мягкий штраф). Подозрительные значения код не выбирают |
| Сборка | `ml/pipeline.py` | `analyze()` — весь пайплайн, итоговый JSON |
| Справочник | `ml/ktru.py` | чтение `data/processed/ktru.parquet` (результат парсера `ml/data/`): только действующие конечные позиции, без шаблонов и услуг (1209 позиций); характеристики, помеченные в архиве `actual: false`, не загружаются |

**Иерархия источников характеристик** (поле `origin`): `ktru` — характеристика и значение из справочника КТРУ;
`portal` — нет в КТРУ, но есть на Портале поставщиков: в карточках СТЕ этого товара или в справочнике характеристик
категории; `new` — нет ни там, ни там, сохраняем как новую;
`answer` — выбрана пользователем из вариантов КТРУ. В сужении кодов КТРУ участвуют только `ktru` и `answer`.
Между Порталом и новой — уровень «встречалась раньше»: HTTP-сервис сохраняет каждую `new` в Postgres и помечает
`known: true`, если она уже была в другом описании того же товара (см. «Новые характеристики» ниже).

**Распознаваемые ошибки** (`severity: error`): опечатки и раскладка (с исправлением), несуществующее значение
(«материал бойка деревянный», «молоток с деревянным бойком» → допустимы Алюминий, Медь, Сталь; «ростовая группа 15»,
«размер 300»), неподходящая единица («длина рукоятки 2 кг»), число вне допустимых диапазонов, противоречие в
описании («с подлокотниками без подлокотников»), противоречие оставшимся товарам, товар не найден в КТРУ,
неверный формат запроса.
**Предупреждения** (`severity: warning`): подозрительное значение — формально в открытом диапазоне КТРУ, но в 3+ раза
дальше крайней границы («стол высотой 5 метров» при границе «≥ 100 см», «молоток 50 кг» при «≥ 2.5 кг»);
ошибки значений, когда позиция КТРУ определена неточно (наименование не совпало с текстом) — это не вина пользователя;
несколько значений одной характеристики («мужская женская»); значение, которого нет в полном справочном списке
Портала; ответ на вопрос, не подходящий ни к одной позиции; не введены обязательные характеристики КТРУ
(`missing_required`: «Вы не ввели обязательные характеристики товара: «Тип каркаса», …»).
**Уведомления** (`severity: info`): `not_in_ktru` — признаки, которых нет среди характеристик КТРУ товара, со списком.

**Словари** (пополнять по ходу тестов): `data/synonyms.json` — синонимы слов пользователя,
`data/value_aliases.json` — обобщающие значения КТРУ.

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Справочник `data/processed/ktru.parquet` уже в репозитории (пересобрать — `scripts/prepare_ktru_dataset.py`).
Словарь Портала `data/processed/portal_characteristics.json` собирается из выгрузок организаторов и в репозиторий
не входит: положить `Инструменты.xlsx`, `Мебель.xlsx`, `Одежда.xlsx` в `data/raw/supplier_portal/` и выполнить
`python -m ml.portal build` (около 6 минут, ~11 МБ). Без словаря уровень «portal» пропускается, характеристики вне КТРУ идут как `new`.
После обновления `ml/portal.py` словарь нужно пересобрать.
Словарь состоит из двух частей. Справочник категории (вкладка 2): название попадает в него, если встречается
минимум в двух категориях Портала (КПГЗ). Профили товаров (вкладка 1, колонка «Характеристики» карточек СТЕ):
для товара — категория + главное слово названия, от 20 карточек — какие характеристики заполнены минимум
в 3 карточках и в 1 % карточек товара, и с какими значениями. В обе части идут только актуальные характеристики
(`is_actual` в `ml/portal.py`): класс «Базовая» или «Эталонная», не «Категореобразующая», заполнена в карточках.
`python -m ml.portal build --holdout 10 --out <файл>` собирает словарь без каждой десятой карточки — для проверки
на отложенных.
Runtime использует только `status == ACTIVE` и `is_template == False`: 1238 позиций из 1839 подготовленных.
При первом запуске скачивается модель (~470 МБ) и считаются эмбеддинги КТРУ (кэш в `data/cache/`).
Рядом с `.npy` сохраняется manifest: модель, версия retrieval-document strategy, hash датасета и размерность эмбеддинга.
Старый кэш от другой document strategy не используется.
Видеокарта не нужна.

## Как пользоваться

```python
from ml.pipeline import Pipeline

p = Pipeline()   # один раз при старте сервиса
r = p.analyze("стл на металлическом каркасе, без подлокотников")
```

Пока в ответе нет `ktru`, показываем пользователю `next_step` и передаём его выбор в `answers`
вместе с исходным текстом:

```python
r = p.analyze({
    "raw": "стл на металлическом каркасе, без подлокотников",
    "answers": [
        {"type": "product", "value": "Стул на металлическом каркасе"},                      # next_step.type = product
        {"type": "characteristic", "characteristic": "Наличие мягкого сидения", "value": "Да"}  # next_step.type = characteristic
    ]
})
```

Ответ на вопрос с `type: code` — `{"type": "code", "value": "<код>"}`.
Можно передать токены от бэкенда в поле `tokens` (`{text, lemma, span, known}`), иначе пайплайн токенизирует сам.

### Формат ответа

```json
{
  "input": "стл на металлическом каркасе",
  "text": "стул на металлическом каркасе",
  "corrections": [
    {"from": "стл", "to": "стул", "span": [0, 3], "reason": "опечатка (отличается на 1 симв.)", "alternatives": ["стол"]}
  ],
  "characteristics": [
    {"name": "Тип каркаса", "value": "Металлический", "unit": null, "source": "металлическом", "span": [8, 21], "method": "stem", "confidence": 0.85, "origin": "ktru"},
    {"name": "Высота", "value": "1100–1200", "unit": "Миллиметр", "user_value": "1100 Миллиметр", "source": "110 см", "span": [30, 36], "method": "number", "confidence": 0.95, "origin": "ktru"},
    {"name": "Цвет", "value": "синий", "unit": null, "source": "цвет синий", "span": [38, 48], "method": "portal", "confidence": 0.7, "origin": "portal"},
    {"name": "Противоскользящие ножки", "value": "Да", "unit": null, "source": "противоскользящие ножки", "span": [50, 73], "method": "new", "confidence": 0.5, "origin": "new", "known": false}
  ],
  "category": "мебель",
  "candidates": [{"code": "31.01.11.150-00000003", "name": "Стул на металлическом каркасе", "score": 0.92}],
  "candidates_total": 4,
  "errors": [
    {"type": "nonexistent_value", "severity": "error", "characteristic": "...", "source": "...", "span": [0, 0], "message": "Значение «…» недопустимо …", "suggestion": "…"},
    {"type": "suspicious_value", "severity": "warning", "characteristic": "Высота", "source": "5 метров", "span": [0, 0], "message": "Значение «5 метров» … выглядит подозрительно: это в 5 раз больше самой крупной границы КТРУ (100 Сантиметр) …"}
  ],
  "next_step": {"type": "characteristic", "message": "Подходит 4 кодов КТРУ. Уточните характеристику «…»:", "characteristic": "…", "options": ["Да", "Нет"]},
  "ktru": null,
  "ktru_name": null,
  "steps": [{"stage": "Поиск по описанию", "count": 23}, {"stage": "Наименование: «Стул на металлическом каркасе»", "count": 4}],
  "timings_ms": {"correct": 0.3, "search": 6.1, "values": 0.8, "narrow": 0.1}
}
```

- `span` у исправлений опечаток — позиции в `input`; у характеристик и приведения к значениям КТРУ — в `text`.
- `errors[].type`: `nonexistent_value`, `out_of_range`, `unit_mismatch`, `conflict`, `contradiction`, `product_not_found`,
  `invalid_input` (error); `suspicious_value`, `multiple_values`, `portal_unknown_value`, `invalid_answer`,
  `missing_required` (warning); `not_in_ktru` (info). `errors[].severity`: `error` (ошибка пользователя),
  `warning` (стоит проверить), `info`.
- `missing_required` — обязательные характеристики КТРУ, которых нет в описании («какие характеристики необходимо
  добавить»): когда код определён — обязательные у этой позиции; пока кодов несколько — только обязательные у всех
  оставшихся позиций (остальное уточняет вопрос `next_step`). Пусто, если товар не найден. Если список не пуст,
  в `errors` есть предупреждение `missing_required` с тем же перечнем.
- `characteristics[].source` — фрагмент текста пользователя, из которого взята характеристика;
  `characteristics[].origin` — источник: `ktru` / `portal` / `new` / `answer`.
- `characteristics[].known` — только у `origin: new` и только в ответе HTTP-сервиса с Postgres: `true`, если
  характеристика уже встречалась в другом описании того же товара. Без Postgres поля нет.
- `category` — категория найденных товаров: `одежда` / `мебель` / `инструменты`; `null`, если товар не найден.
- `next_step.type`: `product` (выбрать товар), `characteristic` (указать характеристику), `code` (позиции не различаются — выбрать код); `null`, когда код определён или товар не найден.
- `method` у характеристики — как найдено: `exact`, `stem`, `fuzzy`, `synonym`, `alias`, `negation`, `keyword`, `number`, `embedding`, `name` (повторяет название товара), `answer` (ответ пользователя), `portal`, `new`.

## HTTP-сервис модели (`ml/service/`)

HTTP-обёртка над `Pipeline.analyze()` для агрегатора (контракт — `docs/api.md`, раздел 4, ветка
`aggregator-service`). Состояния диалога не хранит: в каждый вызов приходят весь текст и все ответы. Слои:
`app.py` (HTTP) → `analysis.py` (сервисный слой: пайплайн, шаг «встречалась раньше», логи входа и выхода) →
`holder.py` (пайплайн под блокировкой) и `repository.py` (Postgres).

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/analyze` | тело `{"raw": str, "answers": [...], "tokens"?: [...]}` → результат `Pipeline.analyze()` (формат выше) + `known` у новых характеристик |
| `GET` | `/health` | процесс жив: `200 {"status": "ok" \| "degraded", "pipeline": "loading" \| "ready" \| "failed", "postgres": "ok" \| "unavailable" \| "off"}`; `degraded` — Postgres недоступен |
| `GET` | `/ready` | пайплайн загружен: `200 {"status": "ready", "load_seconds": …}`, иначе `503` (`loading` / `failed` + `error`). От Postgres не зависит |

**Новые характеристики (Postgres).** После пайплайна сервисный слой берёт характеристики с `origin: new` (их нет ни
в КТРУ, ни в справочнике Портала) и ищет их в таблице `new_characteristics` по ключу (категория, `product_intent`,
леммы названия без учёта формы и порядка слов). `known: true` — характеристика уже встречалась в **другом** описании
того же товара; затем характеристики текущего описания сохраняются. Описание определяется хэшем нормализованного
текста, поэтому следующий раунд того же диалога (тот же текст + ответы) не делает характеристику известной.
Встреченная впервые характеристика сохраняется, только если подходит товару — `fits_product` в
`ml/service/analysis.py`. Пока это заглушка с TODO, которая принимает всё: распознавание моделью ещё не сделано.
Неподходящая характеристика остаётся в ответе (ничего не выбрасываем), но не сохраняется.
Таблицу сервис создаёт сам при подключении. На сужение кодов КТРУ `known` не влияет. Агрегатор передаёт
`known` и `category` фронтенду.

**Без Postgres сервис деградирует, а не падает:** `/ready` остаётся `200`, `/health` показывает `degraded`, у
`/analyze` пропускается только этот шаг (поля `known` нет). После сбоя шаг пропускается 30 с без ожидания
соединения (иначе каждый запрос ждал бы 1 с), затем пробует снова; подключение восстанавливается само.

Пайплайн (модель + индекс КТРУ) загружается один раз при старте в фоновом потоке (~5–10 с), `/health` отвечает
сразу; пока пайплайн не готов, `/analyze` отдаёт `503 model_not_ready`.

**Ошибки** — формат как у агрегатора, плюс `request_id`:
`{"error": {"code": "...", "message": "...", "request_id": "...", "details"?: [{"loc", "msg", "type"}]}}`.

| HTTP | `code` | Когда |
|---|---|---|
| 422 | `validation_error` | не JSON, нет `raw`, `raw` не строка, `answers` не список, ответ без `value` или без `characteristic` при `type=characteristic`, неизвестный `type` |
| 422 | `text_too_long` / `too_many_answers` | `raw` длиннее `MAX_TEXT_LENGTH` символов / ответов больше `MAX_ANSWERS` |
| 413 | `payload_too_large` | `Content-Length` больше `MAX_BODY_BYTES` |
| 503 | `model_not_ready` | пайплайн ещё грузится или не загрузился |
| 500 | `internal_error` | необработанная ошибка; traceback только в логе, клиент получает короткое сообщение и `request_id` |

Пустой или из одних пробелов `raw` — не ошибка запроса: пайплайн вернёт результат без кода (агрегатор такие тексты
отсекает сам). Неизвестные поля тела игнорируются, `answers: null` = `[]`.

**Параллельные запросы.** `Pipeline.analyze()` не потокобезопасен (состояние вызова хранится в общих объектах,
например `ValueMatcher.last_consumed`; на Mac параллельный вызов модели на MPS роняет процесс). Поэтому вызовы
выполняются в пуле потоков (event loop не блокируется, `/health` отвечает всегда) и сериализуются блокировкой:
один процесс обрабатывает один `analyze` за раз, остальные ждут (`queued_ms` в логе). Масштабировать — числом
процессов/контейнеров, а не потоков.

**Логи** (stdout, формат из `AGENTS.md`): на каждый запрос строка `ml.service.access` — метод, путь, статус, мс.
Для `/analyze` сервисный слой пишет вход и выход модели:
- `analyze input:` — длина текста, первые 100 символов, ответы пользователя (`тип:характеристика=значение`);
- `analyze:` — категория, товар (`product_intent`), кандидаты после поиска и после сужения, первые 3 кода, код КТРУ,
  характеристики `название=значение (origin, known)`, число известных, типы ошибок, `next_step`, статус шага
  Postgres (`ok` / `failed` / `skipped` / `off` / `-` — нечего проверять), `queued_ms`, `pipeline_ms`, `postgres_ms`;
- на `DEBUG` — полный запрос и полный ответ JSON (`analyze input (full)`, `analyze output (full)`).

Недоступный Postgres — `WARNING` от `ml.service.analysis` (шаг пропущен) и от `psycopg.pool` (попытки подключения).
`request_id` берётся из заголовка `X-Request-ID` (символы `A-Za-z0-9._:-`, до 128) или генерируется, возвращается в
заголовке ответа и пишется во все строки лога этого запроса. Полный текст описания — только на `DEBUG`.

**Переменные окружения**

| Переменная | По умолчанию | Описание |
|---|---|---|
| `HOST` / `PORT` | `0.0.0.0` / `8001` | адрес сервиса |
| `LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR` |
| `KTRU_PATH` | `data/processed/ktru.parquet` | другой файл справочника |
| `MAX_TEXT_LENGTH` | `5000` | максимум символов в `raw` (у агрегатора 2000) |
| `MAX_ANSWERS` | `100` | максимум ответов в `answers` |
| `MAX_BODY_BYTES` | `262144` | максимум размера тела запроса |
| `POSTGRES_DSN` | не задан (в Docker Compose — `postgresql://ktru:…@postgres:5432/ktru`) | Postgres для новых характеристик; не задан — шаг «встречалась раньше» выключен (`postgres: off`) |
| `OMP_NUM_THREADS` | в Docker `4` | потоки torch; без ограничения в контейнере p50 растёт с ~12 до ~106 мс |

Неверное значение переменной — сервис не стартует (код выхода 2, причина в логе).

### Запуск локально

```bash
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m ml.service                     # http://localhost:8001
curl -s localhost:8001/ready
curl -s -X POST localhost:8001/analyze -H 'Content-Type: application/json' -H 'X-Request-ID: demo-1' \
     -d '{"raw": "стол письменный", "answers": []}'
curl -s -X POST localhost:8001/analyze -H 'Content-Type: application/json' \
     -d '{"raw": "стол письменный", "answers": [{"type": "characteristic", "characteristic": "Тип каркаса", "value": "Деревянный"}]}'
```

Второй запрос (ответ на `next_step` первого) возвращает `"ktru": "31.01.10.000-00000004"`.

### Запуск в Docker

```bash
docker build -f ml/Dockerfile -t ktru-model .      # из корня репозитория; ~3 ГБ (CPU-torch + модель)
docker run --rm -p 8001:8001 ktru-model
# со словарём Портала (в образ не входит — данные организаторов):
docker run --rm -p 8001:8001 \
  -v "$PWD/data/processed/portal_characteristics.json:/app/data/processed/portal_characteristics.json:ro" ktru-model
```

Модель `intfloat/multilingual-e5-small` скачивается при сборке и лежит в образе, эмбеддинги КТРУ считаются при сборке
(`data/cache`), поэтому контейнер стартует без сети (`HF_HUB_OFFLINE=1`) за ~5 с. Пользователь в контейнере
не root, `HEALTHCHECK` — по `/ready` (контейнер `healthy`, только когда пайплайн загружен).

## Проверка

```bash
.venv/bin/python -m eval.try                       # ввод описаний вручную, вывод по шагам (--json — полный ответ)
.venv/bin/python -m eval.make_ktru_cases           # 325 тестовых запросов из реального КТРУ → eval/cases_ktru.jsonl
.venv/bin/python -m eval.run --cases eval/cases_ktru.jsonl -v   # метрики + разбор ошибок
.venv/bin/python -m eval.run                       # регрессия на временных данных (data/mock)
.venv/bin/python -m eval.portal make && .venv/bin/python -m eval.portal run -v   # реальные карточки Портала
.venv/bin/python -m pytest -q                      # юнит-тесты
```

Метрики: `name@1`/`name@5` — правильное наименование первым / в пятёрке поиска; `code_kept` — правильный код
не потерян при сужении; `false_not_found` — товар ошибочно не найден; `chars_P/R/F1` — точность и полнота характеристик.
Каждый запрос прогоняется также с искусственными опечатками (`eval/noise.py`).

### Реальные карточки Портала поставщиков

1200 запросов из `data/raw/supplier_portal/*.xlsx`: название СТЕ как пишут поставщики (бренды, модели, артикулы)
и название + 2 характеристики карточки. Кода КТРУ в выгрузках нет, эталон — категория файла.

| | Товар найден | Категория верна | Характеристик на запрос | Ошибок на 100 | Предупреждений на 100 | мс |
|---|---|---|---|---|---|---|
| Инструменты | 0.90 | 0.97 | 1.1 | 1.3 | 16.5 | 17 |
| Мебель | 0.84 | 0.96 | 2.2 | 5.0 | 9.8 | 15 |
| Одежда | 0.65 | 0.99 | 2.0 | 11.3 | 6.0 | 17 |
| **Всего** | **0.79** | **0.97** | **1.8** (КТРУ 1113, Портал 663, новые 346) | **5.8** | **10.8** | **16** |

«Не найдено» у одежды — в основном рюкзаки и сумки: в КТРУ их нет среди категории «одежда». Карточки реальные,
поэтому ошибки на них — это в основном ложные срабатывания или расхождения Портала с КТРУ; до исправлений
(артикулы как числа, слова товара как названия характеристик, предлоги) их было 30.6 на 100.

## Выбор retrieval

Production retrieval:

- модель: `intfloat/multilingual-e5-small`;
- corpus: 1238 актуальных конечных позиций КТРУ;
- document strategy: `name + nsi_description + characteristic names`;
- quantitative ranges и все допустимые значения в retrieval document не добавляются;
- `name_boost = 0.05`, настраивается в `ml/config/retrieval.json`;
- FRIDA, BGE-M3 embeddings и BGE reranker не входят в production path.

Synthetic benchmark: 325 воспроизводимых запросов, сгенерированных из КТРУ. Это честно сравнивает варианты между собой,
но оценка оптимистичная: запросы построены из того же справочника, по которому ищем.

Финальный прогон production-варианта:

| Corpus | Recall@1 | Recall@5 | Recall@10 | Recall@20 | MRR | mean ms | p95 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1238 | 0.6431 | 0.9354 | 0.9785 | 0.9908 | 0.7790 | 6.36 | 7.46 |

Сравнение моделей на benchmark показало, что FRIDA и BGE-M3 не дают оправданного выигрыша относительно latency/RAM.
CrossEncoder reranker немного повышает Recall@1/MRR, но добавляет сотни миллисекунд на запрос и не включён в hot path.
Порог «товар не найден» (`NOT_FOUND_*` в `ml/pipeline.py`) подобран под шкалу e5-small — при смене модели его нужно перенастроить.

## Ограничения и что дальше

- Синтетические запросы из КТРУ дают оптимистичную оценку; на карточках Портала есть только грубый эталон (категория).
- Неоднозначные опечатки («стл» = стол / стул) решаются по контексту не всегда — второй вариант в `alternatives`.
- Числа без единицы и без названия характеристики внутри фразы («стол 120») не разбираются — неоднозначно;
  отдельным фрагментом («куртка, 48») число сопоставляется с числовыми значениями КТРУ (размер, ростовая группа).
- Порог подозрительного значения — в 3 раза дальше крайней границы КТРУ (`SUSPICIOUS_FACTOR` в `ml/units.py`).
- Пороги (`NOT_FOUND_*`, `FUZZY_MIN`, `EMB_MIN`) подобраны вручную.
