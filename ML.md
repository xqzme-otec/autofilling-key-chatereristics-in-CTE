# ML-пайплайн: описание товара → характеристики КТРУ → код КТРУ

На вход — текстовое описание товара на естественном языке (с опечатками, неполное).
На выход — готовый JSON: исправления, унифицированные характеристики со значениями и единицами,
кандидаты КТРУ, ошибки с обоснованием, следующий уточняющий вопрос и итоговый код.

## Что сделано

| Этап | Файл | Что делает |
|---|---|---|
| Предобработка | `ml/text.py` | нормализация (ё, кавычки, «х/б»), токены, леммы (pymorphy3) |
| Исправление слов | `ml/correct.py` | опечатки, пропуски и перестановки букв, неверная раскладка → слова КТРУ (SymSpell по словарю КТРУ); при нескольких вариантах выбирает по контексту, остальные отдаёт в `alternatives` |
| Поиск кандидатов | `ml/search.py` | семантический поиск по позициям КТРУ (эмбеддинги `intfloat/multilingual-e5-small`) по документу `name + nsi_description + characteristic names`; `name_boost` настраивается в `ml/config/retrieval.json` |
| Текстовые значения | `ml/values.py` | слова пользователя → значения КТРУ: синонимы («кожзам» → «Искусственная кожа»), обобщения («хб» → «Натуральная»), отрицания («без капюшона» → «Отсутствует»), Да/Нет-характеристики («на колесиках» → «Наличие колесных опор: Да») |
| Числа и единицы | `ml/units.py`, `ml/numwords.py` | «110 см», «0,5кг», «52-54», «от 100 до 200 мм», «полтора килограмма» → перевод в единицу КТРУ и попадание в диапазон; число без характеристики КТРУ у товара уходит в Портал / новые |
| Портал и новые | `ml/portal.py` | признаки из описания, которых нет среди характеристик КТРУ товара (в любом месте текста): справочник характеристик Портала (вкладка 2 выгрузок) — «цвет синий» → «Цвет: синий», «в кейсе» → «Упаковка: Кейс»; иначе новая характеристика — «с противоскользящей рукояткой» → «Противоскользящая рукоятка: Да», «гарантия 3 года» → «Гарантия: 3 года». Ничего не выбрасываем; пользователь получает уведомление `not_in_ktru` |
| Сужение | `ml/narrow.py` | наименование → характеристики → уточняющий вопрос (какой товар / какая характеристика / какой код); история шагов; список недостающих обязательных характеристик. Кандидат отбрасывается только при прямом противоречии справочнику; без характеристики — остаётся, но ниже (мягкий штраф). Подозрительные значения код не выбирают |
| Сборка | `ml/pipeline.py` | `analyze()` — весь пайплайн, итоговый JSON |
| Справочник | `ml/ktru.py` | чтение `data/processed/ktru.parquet` (результат парсера `ml/data/`): только действующие конечные позиции, без шаблонов и услуг (1209 позиций) |

**Иерархия источников характеристик** (поле `origin`): `ktru` — характеристика и значение из справочника КТРУ;
`portal` — нет в КТРУ, но есть в справочнике Портала поставщиков; `new` — нет ни там, ни там, сохраняем как новую;
`answer` — выбрана пользователем из вариантов КТРУ. В сужении кодов КТРУ участвуют только `ktru` и `answer`.

**Распознаваемые ошибки** (`severity: error`): опечатки и раскладка (с исправлением), несуществующее значение
(«материал бойка деревянный», «молоток с деревянным бойком» → допустимы Алюминий, Медь, Сталь; «ростовая группа 15»,
«размер 300»), неподходящая единица («длина рукоятки 2 кг»), число вне допустимых диапазонов, противоречие в
описании («с подлокотниками без подлокотников»), противоречие оставшимся товарам, товар не найден в КТРУ,
неверный формат запроса.
**Предупреждения** (`severity: warning`): подозрительное значение — формально в открытом диапазоне КТРУ, но в 3+ раза
дальше крайней границы («стол высотой 5 метров» при границе «≥ 100 см», «молоток 50 кг» при «≥ 2.5 кг»);
ошибки значений, когда позиция КТРУ определена неточно (наименование не совпало с текстом) — это не вина пользователя;
несколько значений одной характеристики («мужская женская»); значение, которого нет в полном справочном списке
Портала; ответ на вопрос, не подходящий ни к одной позиции.
**Уведомления** (`severity: info`): `not_in_ktru` — признаки, которых нет среди характеристик КТРУ товара, со списком.

**Словари** (пополнять по ходу тестов): `data/synonyms.json` — синонимы слов пользователя,
`data/value_aliases.json` — обобщающие значения КТРУ.

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Справочник `data/processed/ktru.parquet` уже в репозитории (пересобрать — `scripts/prepare_ktru_dataset.py`).
Словарь Портала `data/processed/portal_characteristics.json` собирается из выгрузок организаторов и в репозиторий
не входит: положить `Инструменты.xlsx`, `Мебель.xlsx`, `Одежда.xlsx` в `data/raw/supplier_portal/` и выполнить
`python -m ml.portal build` (~7 с, ~3.7 МБ). Без словаря уровень «portal» пропускается, характеристики вне КТРУ идут как `new`.
После обновления `ml/portal.py` словарь нужно пересобрать.
Runtime использует только `status == ACTIVE` и `is_template == False`: 1238 позиций из 1839 подготовленных.
При первом запуске скачивается модель (~470 МБ) и считаются эмбеддинги КТРУ (кэш в `data/cache/`).
Рядом с `.npy` сохраняется manifest: модель, версия retrieval-document strategy, hash датасета и размерность эмбеддинга.
Старый кэш от другой document strategy не используется.
Видеокарта не нужна.

## Как пользоваться

```python
from ml.pipeline import Pipeline

p = Pipeline()   # один раз при старте сервиса
r = p.analyze("стл на металлическом каркасе, без подлокотников")
```

Пока в ответе нет `ktru`, показываем пользователю `next_step` и передаём его выбор в `answers`
вместе с исходным текстом:

```python
r = p.analyze({
    "raw": "стл на металлическом каркасе, без подлокотников",
    "answers": [
        {"type": "product", "value": "Стул на металлическом каркасе"},                      # next_step.type = product
        {"type": "characteristic", "characteristic": "Наличие мягкого сидения", "value": "Да"}  # next_step.type = characteristic
    ]
})
```

Ответ на вопрос с `type: code` — `{"type": "code", "value": "<код>"}`.
Можно передать токены от бэкенда в поле `tokens` (`{text, lemma, span, known}`), иначе пайплайн токенизирует сам.

### Формат ответа

```json
{
  "input": "стл на металлическом каркасе",
  "text": "стул на металлическом каркасе",
  "corrections": [
    {"from": "стл", "to": "стул", "span": [0, 3], "reason": "опечатка (отличается на 1 симв.)", "alternatives": ["стол"]}
  ],
  "characteristics": [
    {"name": "Тип каркаса", "value": "Металлический", "unit": null, "source": "металлическом", "span": [8, 21], "method": "stem", "confidence": 0.85, "origin": "ktru"},
    {"name": "Высота", "value": "1100–1200", "unit": "Миллиметр", "user_value": "1100 Миллиметр", "source": "110 см", "span": [30, 36], "method": "number", "confidence": 0.95, "origin": "ktru"},
    {"name": "Цвет", "value": "синий", "unit": null, "source": "цвет синий", "span": [38, 48], "method": "portal", "confidence": 0.7, "origin": "portal"},
    {"name": "Противоскользящие ножки", "value": "Да", "unit": null, "source": "противоскользящие ножки", "span": [50, 73], "method": "new", "confidence": 0.5, "origin": "new"}
  ],
  "candidates": [{"code": "31.01.11.150-00000003", "name": "Стул на металлическом каркасе", "score": 0.92}],
  "candidates_total": 4,
  "errors": [
    {"type": "nonexistent_value", "severity": "error", "characteristic": "...", "source": "...", "span": [0, 0], "message": "Значение «…» недопустимо …", "suggestion": "…"},
    {"type": "suspicious_value", "severity": "warning", "characteristic": "Высота", "source": "5 метров", "span": [0, 0], "message": "Значение «5 метров» … выглядит подозрительно: это в 5 раз больше самой крупной границы КТРУ (100 Сантиметр) …"}
  ],
  "next_step": {"type": "characteristic", "message": "Подходит 4 кодов КТРУ. Уточните характеристику «…»:", "characteristic": "…", "options": ["Да", "Нет"]},
  "ktru": null,
  "ktru_name": null,
  "steps": [{"stage": "Поиск по описанию", "count": 23}, {"stage": "Наименование: «Стул на металлическом каркасе»", "count": 4}],
  "timings_ms": {"correct": 0.3, "search": 6.1, "values": 0.8, "narrow": 0.1}
}
```

- `span` у исправлений опечаток — позиции в `input`; у характеристик и приведения к значениям КТРУ — в `text`.
- `errors[].type`: `nonexistent_value`, `out_of_range`, `unit_mismatch`, `conflict`, `contradiction`, `product_not_found`,
  `invalid_input` (error); `suspicious_value`, `multiple_values`, `portal_unknown_value`, `invalid_answer` (warning);
  `not_in_ktru` (info). `errors[].severity`: `error` (ошибка пользователя), `warning` (стоит проверить), `info`.
- `missing_required` — обязательные характеристики КТРУ оставшихся позиций, которых нет в описании
  («какие характеристики необходимо добавить»).
- `characteristics[].source` — фрагмент текста пользователя, из которого взята характеристика;
  `characteristics[].origin` — источник: `ktru` / `portal` / `new` / `answer`.
- `next_step.type`: `product` (выбрать товар), `characteristic` (указать характеристику), `code` (позиции не различаются — выбрать код); `null`, когда код определён или товар не найден.
- `method` у характеристики — как найдено: `exact`, `stem`, `fuzzy`, `synonym`, `alias`, `negation`, `keyword`, `number`, `embedding`, `name` (повторяет название товара), `answer` (ответ пользователя), `portal`, `new`.

## Проверка

```bash
.venv/bin/python -m eval.try                       # ввод описаний вручную, вывод по шагам (--json — полный ответ)
.venv/bin/python -m eval.make_ktru_cases           # 325 тестовых запросов из реального КТРУ → eval/cases_ktru.jsonl
.venv/bin/python -m eval.run --cases eval/cases_ktru.jsonl -v   # метрики + разбор ошибок
.venv/bin/python -m eval.run                       # регрессия на временных данных (data/mock)
.venv/bin/python -m eval.portal make && .venv/bin/python -m eval.portal run -v   # реальные карточки Портала
.venv/bin/python -m pytest -q                      # юнит-тесты
```

Метрики: `name@1`/`name@5` — правильное наименование первым / в пятёрке поиска; `code_kept` — правильный код
не потерян при сужении; `false_not_found` — товар ошибочно не найден; `chars_P/R/F1` — точность и полнота характеристик.
Каждый запрос прогоняется также с искусственными опечатками (`eval/noise.py`).

### Реальные карточки Портала поставщиков

1200 запросов из `data/raw/supplier_portal/*.xlsx`: название СТЕ как пишут поставщики (бренды, модели, артикулы)
и название + 2 характеристики карточки. Кода КТРУ в выгрузках нет, эталон — категория файла.

| | Товар найден | Категория верна | Характеристик на запрос | Ошибок на 100 | Предупреждений на 100 | мс |
|---|---|---|---|---|---|---|
| Инструменты | 0.90 | 0.97 | 1.1 | 1.3 | 16.5 | 17 |
| Мебель | 0.84 | 0.96 | 2.2 | 5.0 | 9.8 | 15 |
| Одежда | 0.65 | 0.99 | 2.0 | 11.3 | 6.0 | 17 |
| **Всего** | **0.79** | **0.97** | **1.8** (КТРУ 1113, Портал 663, новые 346) | **5.8** | **10.8** | **16** |

«Не найдено» у одежды — в основном рюкзаки и сумки: в КТРУ их нет среди категории «одежда». Карточки реальные,
поэтому ошибки на них — это в основном ложные срабатывания или расхождения Портала с КТРУ; до исправлений
(артикулы как числа, слова товара как названия характеристик, предлоги) их было 30.6 на 100.

## Выбор retrieval

Production retrieval:

- модель: `intfloat/multilingual-e5-small`;
- corpus: 1238 актуальных конечных позиций КТРУ;
- document strategy: `name + nsi_description + characteristic names`;
- quantitative ranges и все допустимые значения в retrieval document не добавляются;
- `name_boost = 0.05`, настраивается в `ml/config/retrieval.json`;
- FRIDA, BGE-M3 embeddings и BGE reranker не входят в production path.

Synthetic benchmark: 325 воспроизводимых запросов, сгенерированных из КТРУ. Это честно сравнивает варианты между собой,
но оценка оптимистичная: запросы построены из того же справочника, по которому ищем.

Финальный прогон production-варианта:

| Corpus | Recall@1 | Recall@5 | Recall@10 | Recall@20 | MRR | mean ms | p95 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1238 | 0.6431 | 0.9354 | 0.9785 | 0.9908 | 0.7790 | 6.36 | 7.46 |

Сравнение моделей на benchmark показало, что FRIDA и BGE-M3 не дают оправданного выигрыша относительно latency/RAM.
CrossEncoder reranker немного повышает Recall@1/MRR, но добавляет сотни миллисекунд на запрос и не включён в hot path.
Порог «товар не найден» (`NOT_FOUND_*` в `ml/pipeline.py`) подобран под шкалу e5-small — при смене модели его нужно перенастроить.

## Ограничения и что дальше

- Синтетические запросы из КТРУ дают оптимистичную оценку; на карточках Портала есть только грубый эталон (категория).
- Неоднозначные опечатки («стл» = стол / стул) решаются по контексту не всегда — второй вариант в `alternatives`.
- Числа без единицы и без названия характеристики внутри фразы («стол 120») не разбираются — неоднозначно;
  отдельным фрагментом («куртка, 48») число сопоставляется с числовыми значениями КТРУ (размер, ростовая группа).
- Порог подозрительного значения — в 3 раза дальше крайней границы КТРУ (`SUSPICIOUS_FACTOR` в `ml/units.py`).
- Пороги (`NOT_FOUND_*`, `FUZZY_MIN`, `EMB_MIN`) подобраны вручную.
